## 実接続で見つけた修正

- 不正な分解作業IDは保存前に拒否する。`key`と`dependsOn`のどこを直すかを、原入力を含めず返す。小文字の英字から始め、英小文字・数字・ハイフンで40文字以内とする。保存・実行未開始と自動再試行なしも明示する。
- 契約サービスの分解案48KBに対し、App Serverの一律8KB入口が不整合だった。実際に8,174 byteの案が入口で拒否された。登録済み計画ツールにだけ、単一案10KB・分解案50KB・プロジェクト読取結果64KBのhost設定を接続した。契約の8KB/48KB上限や権限確認は維持する。
- 通常ツールの既定は入力8KB・結果24KB。上限の情報はproviderに渡さず、登録済みのown entryと検証済み数値だけから保存する。特殊名やprototype継承値による上限迂回も独立監査後に修正し、拒否テストを追加した。

## 成功に合算しない試験

最初の不正IDの案は未保存。次の8KB超過も契約保存前に拒否された。別のコード試験では、Sol2件が操作確認を待ったまま5分の期限に達し、照合待ちとなった。読取専用のprovider照合で両方の中断を確認したが、台帳・差分・実行枠を保持した。新しい隔離環境での明示試験を成功として記録し、以前のrunを再送・上書き・受入済みにしていない。

UI補助の30秒待機が統合レビュー登録に間に合わなかった場合も、処理完了とは扱わず、同じ操作の完了を待った。再起動監査の初版は署名付き操作承認のreader不足とCRLFを含むバイト比較で拒否された。製品の承認確認を緩めず、正規のreaderと改行変換を明示した監査で再確認した。
