# 固定した元成果を解決Taskへ渡す

変更範囲が重なる検証済みTaskを、明示確認した新しい契約と一つのSol作業場所でまとめる。Material 3 Expressiveの統合相談、統括の契約案カード、契約確認、Task実行、通常レビューを接続する。

## 操作

1. 統合画面の相談カードから、選択した成果入りの依頼文を統括へ送る。
2. 設定済みAstraが`negi_read_integration_sources`で現在の固定原文・契約・仕様参照・検証を読む。`negi_read_project`で今回の仕様も読み、推測した元成果を使わない。
3. 同じ選択hashを指定し、`negi_propose_resolution_task`で元成果の全受入条件をそのまま含む案を保存する。ここではモデル実行・Vault契約・worktreeを開始しない。
4. チャットの「この契約案を確認」から契約画面を開く。「解決に使う元成果」でタイトル・受入条件・元レビューを確認し、必要なら固定した版と原文を展開する。今回の対象・対象外・保つ条件・実行計画も確認する。
5. 「この契約を確定」で署名付き契約と専用worktreeを準備し、Task画面から明示的に開始する。確認済み計画を直接Solへ渡すため、新しいTask Astraの計画turnは追加しない。
6. 元成果の登録済み検証とprofileの検証を行い、成功した結果を通常レビューへ渡す。検証成功と人間受入は別の状態である。

PCは契約一覧と詳細、スマホは契約選択と一つの詳細を使う。確認ボタンより前に元成果を置く。通常Taskへの切替・取得失敗では前の元成果表示を消し、同じ固定版の更新では展開状態を保つ。

## 固定するもの

- 2〜8件の現在の検証済みコードTask。同じproject/Vault/Git common directory/scheduler/基準SHAを要求し、調査Taskは対象にしない。元成果の人間受入は開始の必須条件ではない。
- 元Task/実行ID、契約版、修正版、設定・manifest・契約・artifactのSHA256、レビューID、検証証拠、受入条件、元契約の条件、全成果原文と仕様参照を固定する。
- 新契約の許可パスは元成果の変更ファイル集合と完全一致させる。元契約の受入条件を削除できない。元Taskの対象外や保つ条件は原文データとして確認に残し、解決作業の範囲と条件は新しい具体的契約で確定する。
- profileと元Taskの検証コマンドをそのまま合成する。同じ検証名の異なるコマンドは拒否する。資源は大小文字を無視して重複除去する。モデル入力からコマンド・モデル・保存先・権限を追加する入口はない。

元成果のGit metadata変更、rename、新規実行ファイルは別の計画が必要。重ならない成果は既存のコピー統合を使う。上限は新契約と実行設定に合わせ、変更パス20、固有受入条件20、継承参照ID50、検証10、資源20。原文JSONは8000文字かつUTF-8で24000バイト以内、仕様と生成Task本文の合計も14000文字以内にする。大きすぎる場合は分解を要求し、原文を切り捨てない。

## 開始直前と復元

元契約を現在のVaultから再exportし、Task原文・完全な仕様参照・snapshotを再照合する。成果の差分、固定artifact、検証、修正版、取消と新解決Task自身の追加仕様も確認する。保存した選択と異なれば、契約確定・開始・scheduler claim・実際の`thread/start`/`turn/start`を保留する。

参加するreader/writerではnative storage→review source guardの順序を保ち、照合から実RPCの応答までguardを保持する。guardによる送信前拒否は既知の失敗、呼出し開始後の例外は結果不明として台帳を分ける。停止と期限も送信直前に確認する。外部の非参加writerをOSレベルで排除する保証ではない。

署名したdraftから開始確認とadmission guardを復元する。再起動だけでモデルを再送しない。元Taskの差分・成果・受入を解決Taskが自動変更することもない。新しい結果も通常レビューで明示的に受け入れる。

### 対応していない実行経路を止める

解決案は`negi-task-plan/2`、確定したTask classと実行設定・scheduler記録は`integration_resolution`を使う。通常の独立Task案へ読み替えない。設定と契約の区分が一致しない、署名した計画がない、元成果を照合するadmissionが復元されていない場合は開始を拒否する。Taskサービスだけを先に復元した場合も、契約サービスが元成果の照合を登録するまでは開始・待機実行を保留する。

standalone/parallel CLIはこの区分を準備・scheduler登録の前に拒否する。低レベルrunnerも署名した計画と照合guardの両方を必要とする。schedulerはSol/write/directだけを許可する。旧readerは新しいdraft/config/scheduler区分を拒否するため、解決Taskを保存する前に参加するreader/writerを一括更新する。古いbinaryを混在させたり、新形式の保存後に旧版へ戻したりする運用は非対応で、外部writerの参加・静止を測定した証拠ではない。

確定時はparserの正規化済み設定を署名し、復元時も同じ設定との完全一致を照合する。署名の一致条件は緩めない。未送信終了・結果不明の照合にも区分を残す。未送信終了の作業記録は設定の担当とread/write権限を引き継ぐため、既存のLuna調査をSol/writeへ変えない。native Luna調査の実行保留は維持する。

## 検証と残る条件

新しい境界試験は実Git/Vault/署名/Task scheduler/Reviewを使い、同じコードファイルを変更した二つの異なる成果から、全原文を受け取った一つのSol fixture、固定計算検証、レビュー待ちまで進む。元checkoutと主checkoutの差分を保持する。参照仕様・成果変更、確認前拒否、thread後turn前の抑止、再起動後の明示QA受入取消による開始拒否も検証する。QA受入は隔離fixtureの明示操作で、製品成果の利用者受入ではない。

実providerでのこの新経路、任意のコード競合の解決品質、部分作成/結果不明の汎用復旧、実機safe-area/仮想キーボード、人の全導線受入は継続する。既存の[実Astra結果伝達](negi-teams-verification-handoff.md)と[別ファイルの実コード統合](negi-teams-code-integration-qa.md)を、この新経路の実モデル試験へ換算しない。native Luna調査の開始保留は維持する。全Phase0〜8／NT-001〜NT-073の完成宣言ではない。
