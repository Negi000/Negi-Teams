# 統括から登録Taskを委任する

2026-10-01。明示設定したCodex chat Masterが、Task画面と同じ固定カタログ・`LocalTaskService`・単一schedulerを使用する接続。

## 起動と操作

既存のCodex Masterのopt-in設定と、起動時の`NEGI_TASK_CONFIG`を使用する。モデル・effort・Codex実行ファイルは明示設定を維持する。通常の統括起動はChatGPT認証を確認してからモデルのthreadを開き、APIキーを子プロセスへ渡さない。CLIの変更は新しい起動設定で確認し、過去のrun設定は書き換えない。

| 操作 | 入力 | 結果 |
|---|---|---|
| `negi_list_task_results` | なし | 同じ統括・会話から委任、または承認済み契約を作成したTaskの固定結果通知と伝達状態、最大8件 |
| `negi_list_tasks` | 任意のproject・offset | 10件ずつの固定カタログ、契約ID・版・設定hash |
| `negi_read_task` | 登録済みrun ID | 完全な固定Task Contract、担当、検証・人間受入・現在の状態 |
| `negi_dispatch_task` | run ID・カタログのconfig hash | Task画面と同じschedulerへの一度だけの開始要求 |

チャットでは「Task結果を確認」「Task一覧を取得」「Task契約を確認」「Taskを委任」と表示する。展開すると操作の識別子と入出力を確認できる。Task画面は利用者の開始と統括からの委任を区別する。古い起動元未記録のrunを利用者操作と推定しない。

## 固定する境界

- serverが登録した4操作だけを通常の固定Taskのproviderへ渡す。workerには渡さない。新規契約の明示設定がある場合は、[追加の3操作](./negi-teams-new-task-authoring.md)で計画参照と案の保存だけを許可する。
- thread・turn・call IDを照合する。同じcallの再送は同じ結果を返し、異なる引数でのcall ID再利用は拒否する。
- 起動要求は会話IDへ結び付けて永続化する。UIとの同時開始やサーバ再起動でも同じTaskを再実行しない。
- 契約・担当モデル・コマンド・checkout・承認・成果受入をモデル入力から変更しない。
- 完全な契約を返せない大きさのTaskは委任前に停止する。切断や結果不明時はTask画面で照合し、自動再試行しない。
- 統括の委任記録は人間の署名付き操作承認・成果受入とは別の記録である。

## 通常チャットの実行枠

Codex chat Masterは`NEGI_TASK_CONFIG`の同じschedulerを使う。稼働中のturnをAstraの読取作業として登録し、枠と作業場所の読取権を確保してから`turn/start`を送る。起動済みで待機しているプロセスは実行枠を占有しない。子プロセスの隠れた委任は引き続き無効。

入力・モデル・effort・会話ID、provider turn ID、終了応答とhashを、モデルの作業場所の外に保存する。Task状態の保存場所が統括の作業場所の中にある設定は未送信として拒否する。API予算との混用を拒否する。役割別の共有枠と、既存設定を保持する移行は下記の追加実装に従う。

- 満席または作業場所の競合ならproviderへ送らず、今回の要求を未送信として取消記録する。入力と引用を保持し、空きができた後に利用者が再送できる。
- 確認できた終了・失敗・中断は証拠保存後に枠を解放する。解放時は同じサービスの待機Taskを再評価する。
- 切断・時間切れ・終了証拠の保存失敗は枠を保持する。自動再送・自動復帰せず、会話IDとturn IDを照合する。
- schedulerのMaster `verified`はprovider終了応答の確認を示す。Task品質の検証や人間の成果受入を示さず、金額は不明のまま。

Material 3のチャットは受付応答を待ってから入力を消す。要求IDが一致する応答または復元された会話だけで受付を確定し、他の送信と混同しない。送信結果の分からない切断では入力を保持し、自動再送しない。未送信の案内は共通のエラー色・14px本文・読上げ通知を使う。

## 計画1・作業2の共有枠

2026-10-01追加。新しいsubscription schedulerの既定は計画1・作業2・合計3。常駐統括のturnとTask内のAstra計画は同じ計画枠を使用する。Sol/Lunaとローカル修正版の検証は作業枠を使用する。

Taskは計画→作業枠待ち→作業を記録する。Astraの終了・thread/turn ID・計画成果のhashを確認すると計画枠を解放する。待機中もcheckout・共有資源の所有権と予算予約を保持する。空きができた時は原子的な作業枠の確保と計画成果・固定契約の再確認を経てSolへ進む。作業2件の間に次の計画を進められるが、計画の同時実行は1件まで。

起動時に読む`NEGI_TASK_CONFIG`のカタログへ、次の任意のプロパティを追加できる。HTTPとモデルの操作からは変更できない。

```json
{ "capacity": { "maxConcurrent": 3, "planners": 1, "workers": 2 } }
```

合計は1〜64、各役割は0〜64の整数。0でその役割の新しい開始を待たせられる。既存schedulerで指定を省略すると従来の合計上限を保持し、未設定の役割上限だけを追加する。従来1枠のschedulerを3枠へ移すには明示設定が必要。設定変更は追記し、過去のログ・Task設定hashを変更しない。上限を下げても実行中の作業は強制終了せず、空くまで新しい開始を待たせる。

結果不明の計画は計画枠、結果不明の作業は作業枠を保持する。古い担当交替未記録のSol書込は、照合できるまで計画・作業の両枠を保守的に占有する。計画終了の証拠がある待機はモデル枠を使用しないが、結果不明になっても作業場所の所有権を保持する。再起動後の自動再開は行わない。

Material 3のTask画面は全プロジェクトの計画・作業・合計、作業枠待ち、照合待ち、旧記録と上限超過を表示する。認証Cookie付き`GET /api/tasks/capacity/summary`は集計値だけを返す。取得失敗時は古い数値を消し、Taskの状態を維持して案内する。開始待ちと計画完了後の作業枠待ちも区別する。

## Task結果の通知と統括への伝達

Taskの終了・停止・実行前失敗・照合が必要な結果を、認証付き作業一覧と委任元の統括チャットへ返す。カードは共通のMaterial 3 Expressiveの色・shape・48px以上の操作を使い、Taskと現在の成果レビューへ移動できる。通知で入力中の下書きや応答streamを閉じない。作業一覧の統括欄も実際のchat状態を表示し、停止中と待機中を区別する。

- 現在の起動カタログに一致するrun/config hashだけを通知一覧と自動伝達の対象にする。設定から外したrunの履歴は保持する。成果の変更検知はレビュー接続時の固定差分照合を利用し、レビュー未設定時に成果ファイルの現状を保証しない。
- 初回結果を固定記録として保存する。修正版・受入・取消・状態変更は前の通知IDに連結した新通知として追記し、元の通知と伝達記録を変更しない。通知番号・成果修正版・契約版を区別する。
- 次の利用者の通常送信に、同じMaster IDと会話IDから委任した最新の未伝達結果を最大8件添える。Task設定hash・台帳・scheduler・現在の成果を準備時と送信記録の確定時に再確認する。準備済み通知が更新されていれば今回の入力を未送信として保留する。
- 通知表示だけではprovider turnを起動しない。別の会話やTask画面からの依頼を自動で統括へ送らない。
- 投入前・投入中・provider turnへの結付け・終了観測・既知の未送信・結果不明を追記台帳で区別する。送信本文と終了観測は作業場所の外に保存し、hashで照合する。
- 確実な未送信だけが、次の利用者送信で再び候補となる。再起動・再接続はprepared/dispatching/bound/unknownの結果を再送しない。応答不明・結付けや終了証拠の保存失敗はMasterの枠を保持する。
- 「統括の応答を確認」はproviderの終了応答を保存した意味で、内容の理解・成果品質・人間受入の証明ではない。
- 起動時の復元は保存済みTaskの事実を読む。新しいTask/model turnを始めない。復元失敗はTask画面での照合へ案内し、起動済みMasterを作り直さない。
- 結果一覧はCookie認証を必要とするGET `/api/tasks/results/summary`。POSTは拒否し、通知取得失敗では古い通知を消してTask/レビューの取得結果を維持する。

### 通知の版更新と運用（2026-10-02）

この追加で、上記の修正版・受入・取消後の通知再発行を接続した。通常完了ではowner完了処理とlive状態の解除後に初回通知を発行する。通知append失敗は成果・受入判断を取り消さず、「操作は保存済み、通知更新は未完了」と表示する。一覧の再読み込みと委任元の次の送信で保存済みTaskから通知を修復する。モデルや検証は再実行しない。旧通知のunknown等を再送可能に戻さず、異なる新結果だけを別の伝達対象にする。作業一覧はrunごとの最新、チャットは「新しい結果あり」を添えた履歴を表示する。

Review storage全体の安定した`result-source.lock`を、受入・取消・コメント、Task修正版採用/レビュー同期/照合終了、通知発行と送信記録の確定で共有する。複数runを含む送信も共通ロック下で照合する。機械検証はロック外で実行し、採用前にTask/Review全状態とGit HEAD・diff・変更ファイルhashを再照合する。現在の訂正を一部だけ置き去りにせず、今回の新要件には新契約を要求する。検証中の既知の変更は未採用として検証枠をfailed精算する。capture中の変更や部分保存は照合待ちで証拠・枠を保持する。

送信記録の確定が観測境界であり、その後の受入・取消や外部Git/file編集を凍結する仕組みではない。確定後の変化は別通知とし、保存済み入力とprovider receiptを書き換えない。手動の台帳編集、別storageのwriter、外部Git/file変更には共通ロックの排他性を保証しない。

検証中は外部のeditor/CLI/別providerで対象checkoutを変更しない運用が前提である。前後の同じhashは途中変更がなかった証明ではなく、検証中だけA→B→Aへ戻す外部writerは検出できない。不変snapshot上での検証と成果captureの結合は残る条件である。実行中/待機中のTask状態読取は成果のadopt/syncを行わず、先行成果のadmission照合と競合して状態を読めなくしない。

#### 通知形式の更新とdowngrade

新readerは既存`results.jsonl`の初回通知・配送記録を保持して読む。更新情報を初めて追記する前に、旧logの正確なbytes/hashを同じdirectoryの`pre-v2-log.json`へ排他的に保存する。archiveの部分保存/改変時は追記を止める。元log、入力、終端artifactは保持する。

**更新通知を記録した後の旧binaryへのdowngradeは非対応**。旧readerは同じrunの複数通知を拒否する。旧logだけへ戻すと新しい受入取消・伝達記録を失うため、archiveで稼働logを上書きしない。更新前に全writerを停止し、Task/Review/scheduler/通知storageと入力・終端artifactを一体でバックアップする。更新後の障害は同じ形式を読める修正版でroll forwardする。backupは監査と隔離された読取確認に使う。自動downgrade/形式変換は提供しない。

#### 残留source lockの手動照合

owner記録はschema・ランダムID・PID・取得時刻をfsyncする。競合は2秒まで待ち、レビュー操作中として保留する。既存のadmission待機はbusyを再試行する。古い時刻だけでlockを消さず、kill後の残留や部分owner記録を自動復旧しない。

1. 同じReview storageを使う全サーバー/CLIを停止する。設定から解決した絶対storage path内の当該lockであることを確認する。
2. storage一式・Task台帳・scheduler・proof・入力/終端artifactをバックアップし、lockのID/PID/時刻を記録する。所有者と関連処理の終了を照合する。PID再利用や空/部分owner記録を終了の証拠にしない。
3. 台帳の完全な行末・hash・署名と、途中の修正版/受入/取消/配送状態を確認する。不明な保存があればlockを保持して個別照合する。provider/Task ownerの残留をこのlockの移動だけで解消しない。
4. 全writer終了と証拠の完全性を確認できた場合だけ、当該lockを検証済みstorage内の別名へ退避して原記録を残し、同じ新形式で起動する。一覧から再照合する。unknown配送を再送へ戻さず、モデル/Taskを再投入しない。

これは運用手順であり、全crash条件や汎用lock復旧の実証ではない。通常解放、合成の残留ownerの非削除/保留、通知更新失敗後の読取修復を試験した。

## 2026-10-03追加: 契約案を作った会話への結果通知

統括の案を契約画面で確定し、Task画面から開始した作業の結果を、契約案を作った同じ会話へ返す。実行を開始した`origin.kind: browser`は保持し、署名済みの契約承認から取得した`createdBy`を別に保存する。run/config/vault/model/effortと四つの会話・操作IDを照合する。承認の読取では保存先や署名keyを作らず、不足・改変は保留する。

Material 3の作業一覧とチャットには、利用者がTask画面から開始した結果、伝達状態、現在のTask/成果レビュー、「契約案を作った会話」への参照を表示する。現在のthreadへ宛てた結果だけがチャットに表示される。legacy構成でも別threadの通知を混ぜず、現在のthreadが不明な場合は作業一覧から確認する。通知は下書き・streamを終了させない。

通知だけではモデルturnを開始しない。同じ会話の次の明示入力で現在のTask/レビューを照合し、最大8件の固定結果を一度だけ添付する。登録ツールからも同じ範囲の結果を取得できる。dispatch前に再照合し、結果不明の配送は再読み込みや再起動で再送しない。人間受入は結果の伝達とは別に維持する。

既存のbrowser通知に作成元を追加する場合は、署名済みの承認と固定設定から新しい状態通知を作り、旧通知・原文bytesを保持する。一度記録した作成元は変更・削除できない。元の委任通知とその配送記録は従来の会話へ束縛する。登録済み8ツールの定義・schema・配列順は直前の公開版と同一で、これらの変更による常駐会話の設定hash移行は発生しない。更新後の旧binaryへのdowngradeは上記の方針を維持する。

Task開始要求を保存してから事前確認が終わるまで、同じserviceが所有している操作は「実行待ち」として表示する。ここでは停止可能なproviderはまだ存在しない。別serviceや再起動後にはprocess内の所有証拠がないため「照合が必要」を維持し、同じ開始要求の照会も再投入しない。事前確認の失敗は実行前失敗として保存する。

新しい事前確認失敗は、後続の結果読取より先に`negi-task-preflight-failure/1`として保存する。段階（契約/認証等のprepare、schedulerへのsubmission）、固定allowlistのerror code、時刻、公開分類だけのhashを含む。元の例外message/stack/path/tokenは保存もhash化もしない。失敗だけでは登録intentの不在を確定できないため`schedulerSubmission`はunknownを維持する。旧失敗記録も読み取れるが、失われた例外を遡って復元しない。この時点で未接続だった読取helper停止と未実行要求の明示終了は、[開始前の失敗の復旧](negi-teams-preflight-recovery.md)で追加した。同じ要求の再試行と未知の登録intentの再送は許可しない。

今回の進捗はNT-004/008/051/064/067/073に対応する。未知のprovider結果の汎用復旧、旧dispatchの全面移行、任意の成果の品質、実機と利用者による受入は引き続き残る。最新の試験と実provider/UI観測は[実装状況](negi-teams-implementation-status.md)に記録する。
