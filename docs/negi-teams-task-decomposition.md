# 大きい依頼の分解案と独立Task

常駐Astraの通常のTask toolsに`negi_propose_task_decomposition`を追加した。一つの大きい依頼を2〜8件の契約案へ分け、Material 3 Expressiveの契約画面で全体の目的、共有条件、各作業の依存と引継ぎ成果を確認できる。小さい依頼は従来の1件の契約案を使う。

## 操作の流れ

1. 統括が必須仕様の版を読み、各作業の目的・変更可能パス・受入・計画・制限を持つ案を作る。
2. チャットの「分けた作業を確認」から契約画面を開く。PCは一覧と詳細、スマホは契約案の切替と単一詳細を使う。
3. 「依頼全体の作業と引継ぎを確認」で共有条件と先行Taskを確認する。
4. 独立Taskを一つずつ確認して確定する。同じ依頼の独立Taskがすべて登録されるまで、通常のTask画面とnative委任は開始できない。具体的な理由をTask画面へ返し、開始要求やprovider turnを作らない。
5. 確定した独立Taskを、同じscheduler・専用worktree・承認済みAstra計画でSolへ渡す。既存の検証と固定差分レビューを使う。
6. 先行Taskがある案は「先行作業を待っています」と表示する。この案の確定APIも拒否する。成果の統合後、実際の基準SHAを読んで統括に新しい契約案を依頼する。

作業の順番だけを待たせても、別のworktreeへ先行コードが渡ることにはならない。後続を古い基準で開始する操作は、この入口に用意していない。先行Taskの機械検証や人間受入だけで後続を自動確定・実行しない。

## 分解案の形式と固定

| 項目 | 内容 |
|---|---|
| `title` / `objective` | 依頼全体の名前と目的 |
| `coordination` | 共有する条件・インターフェース。1〜8項目 |
| `nodes` | 2〜8件。各nodeに`key`, `dependsOn`, `handoff`, `task` |
| `key` | 同じ案の中で一意な短いID |
| `dependsOn` | 同じ案の先行nodeのID。空なら独立Task |
| `handoff` | 次の作業に渡す成果・確認事項 |
| `task` | 1件の契約案と同じ12項目。検証コマンド・保存先・担当の設定はサーバーが保持 |

存在しない依存、自己依存、循環、IDの重複を拒否する。依存関係で前後に並ばないTask同士は、変更可能パスが一致・親子・Windowsの大文字小文字の別名で重ならないことを確認する。各Taskはprofileの許可パスと制限の上限を守り、案全体は48,000 byte以下に制限する。

全nodeを一つの不変JSONとして保存し、同じ実provider callは同じ分解IDと子のIDを返す。別内容や単一Taskとのcall ID再利用は拒否する。専用Writer lock、100件の子Task上限、必須仕様の版とhash、profile hash、固定HEADを従来の案と共有する。部分的な子ファイルの列挙を実行可能カタログへ足さない。

独立Taskを確定したVault本文に、元の依頼・分解のhash・共有条件・担当node・引継ぎを含め、その本文を署名付き承認と固定exportに結び付ける。未解決の後続はVaultのactive Task・worktree・scheduler entryを生成しない。再起動では、承認と既存worktreeの作成証拠を照合して独立Taskの登録と開始条件を復元し、providerを再送しない。

## 確認した範囲

- 標準TSテスト696件中694成功、失敗0、未完了0、既定skip2。後から追加した独立Taskの全契約確定までの開始条件と画面調整は、関連32件を再実行して全成功。件数を重複加算しない。
- 最終の型検査・ビルド成功。参照変更・HEAD変更・graph改変・同時出版・再起動・確定APIの拒否を含む実Git/Vaultの合成試験で確認した。
- 合成Sol clientの独立2件を同じ通常Task service/schedulerで検証・レビュー待ちまで進めた。追加Astra attempt、後続の起動、人間受入は生成されていない。
- 実HTTP・署名・Git worktree・ビルド済み画面の合成QAで、1件目確定時の開始保留、2件目確定後の開始、文書1件、検証、レビューへの深いリンクを確認した。今回は実モデルを起動していない。
- Chromiumの1440×1000、320×780、375×812、dark、依頼全体と参照詳細の展開、横方向の収まり、48pxの確定操作、キーボードで切替後のフォーカス保持、一覧の確定状態の更新を確認した。consoleのerror/warningは0。画面の見た目を人間受入済みとはしない。

## 残る条件

先行変更の実統合、競合解消、統合基準に基づく後続契約の確定、成果・後続の自動関連付けは未接続。分解案の実Astraによる生成、任意の実コード変更や実機のsafe area・仮想キーボードはこの追加で試験していない。旧dispatchの全面移行、初回profile設定、手動照合、契約の版移行など既存の未完了ゲートも継続する。

全Phase0〜8とNT-001〜NT-073を維持する。分解案を表示できることを、依存グラフ全体の実行・全73要件の完成とは扱わない。

前節の「先行変更の実統合・統合基準に基づく後続契約は未接続」は、この登録済み統合からの限定経路について進展した。通常UIから統合を実行・準備する入口、任意の競合解消、実Astraによる分解と統合後計画、実成果の人間受入、全Phaseと残る各要件の完成を宣言するものではない。
